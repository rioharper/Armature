# Changelog

## Unreleased

- The red-team checklist learns the **derivation decision report** and the **stale price**. Four probes land in the families that already hold their siblings, rather than a new heading: *Routed items* joins §2 Traceability, reading a report's *Items routed here* table against the sources that did the routing — the plan's task line, earlier reports' Route lines, the milestone notes' TBDs — because an item with no row is an item lost, and it was routed because someone judged it load-bearing. §3 gains *Printed, not typed* (run `run_all.py` and match the report's tables against what it prints; a number no module prints was typed by hand and goes stale in silence) and *Book data* (a `standard`-tagged constant names book, edition, and table, and carries the second independent source `derivation-standards.md` asks for, with the design sized to the conservative fit). The existing *Assumptions vs. envelope* probe absorbs the direction-and-size demand instead of being written twice, and the measured-quantity reading stays where it already lives, in the red team's Inputs. *Price staleness* completes the cost rung: a cost row is only as fresh as the `Retrieved` date of the index row it cites, so the probe is that date against today's — over six months unre-read is a Minor, a cost margin that closes only on a price over a year old or thinner than its category's drift is a Major (a Jetson dev kit's list price rose 60 % in nineteen months), a purchase authorised on one is a Blocker — and the fix routes to `armature-librarian`, since re-reading a vendor page needs the web the red team does not have.
- The SolidWorks MCP server is **opt-in per project** rather than bundled into every session. Claude Code gives a plugin no quiet-when-absent mode — a plugin's `.mcp.json` servers connect at session start, there is no per-server enable flag, and the red banner is always the *process* failing, never SolidWorks being closed (`server.py` has attached per tool all along) — so the plugin's root `.mcp.json` is gone. `/armature:init` asks a SOLIDWORKS project its own question, whether to connect the server, and writes that project's `.mcp.json` on a yes; a Fusion, Onshape, or undecided project is quiet by construction, with nothing for the user to toggle off. The written entry is an absolute path into the machine's plugin install, because a *project* `.mcp.json` never expands `${CLAUDE_PLUGIN_ROOT}`, so init's `.gitignore` seed keeps it out of the commit — a teammate cloning the repo inherits no dead path — and init's step-1 guard offers to repoint one that a plugin update stranded, which makes re-running `/armature:init` the documented repair. `sw.py` binds `pythoncom` and `win32com` inside `attach()` instead of at import, so a non-Windows host starts the server and reads `SolidWorks COM needs Windows and pywin32` per tool call rather than dying during import: a failed connection now means one thing, `uv` is not on PATH. Tools move from `mcp__plugin_armature_solidworks__*` to `mcp__solidworks__sw_*`; nothing under `skills/`, `agents/`, or `references/` named the scoped form.
- A derivation that lands as a **report** has a template of its own. `armature-plan`'s `references/derivation-report-template.md` sits beside the bench test template, and the rule that names one now branches on what the task produces: a test task measures and takes the test template, an analysis task run by `armature-derive` decides and takes this one. It carries what the bench shape has no place for — the decision in the section heading rather than a pass/fail against a criterion, a write-back table for every number the report moves, the assumptions under strain with the direction and size the model gives each, and a row per item routed to the task — and it keeps Feeds. `armature-derive` gains the matching section, including the rule that every table is printed from `analysis/model/` so the report re-runs.
- Step 0 gains **the reading of every requirement you size against**: a requirement bounds a measured quantity, and it is rarely the one the wording names — a deceleration and the accelerometer reading of it differ by one g, a joint torque and a motor torque by the reduction. The reading is quoted and written into `00_setup.md` before anything is derived, and wording that admits two readings differing by more than the margin is decided in one sentence and routed back to `armature-spec` (the demo's REQ-025 carried that exact ambiguity through spec, plan, and two milestones before it cost margin). The red team's inputs now name the reading too: a requirement admitting two is a finding even where the artifact picked one, and a reading left unstated is a Question.
- **Design data from a book** — fatigue endurance points, finite-life tables, friction pairs — has no datasheet row for the librarian to cache, so `derivation-standards.md` gives it a rule beside "cite index rows, never memory": tag it `standard` and name book, edition, and table (a book named without its table is memory); find a second independent source and carry both, designing to the conservative one, because two fits disagree — shot-peened wire endurance points differ by 30 % between standard sources that agree within 6 % unpeened, which is a peened coil's whole fatigue margin; pin the disagreement with a self-test; and put the vendor's own basis on the questionnaire, where its answer supersedes both books.
- Budgets: a **reserve is a line item**, and a debit that breaches it fails a check instead of reading as healthy. Nothing debits a reserve directly — its current estimate is the ceiling minus every other line's, so a debit anywhere else debits it in the same edit — and its budget is what its Must requirement demands, so a negative margin is a failed REQ, recorded in the row and in `traceability.md` rather than a hand-written sentence above the table (which is how the demo's REQ-033 reserve fell from 40 g to 8 g under a +30 g spring debit while its row still read 40 g of margin). `Margin is slack` now says which way each kind of row fails: a consumer from above, a reserve from below. The source ladder gains its **cost** rung, `list price`, where `datasheet` sits: a cost row cites the `docs/datasheets/index.md` row whose `Price` cell it read and inherits that row's `Retrieved` as the price's date, so a price goes stale on its own; a part reading `quote only` has no rung above `guess` and the ladder says so, rather than leaving the row looking sourced. `init`'s standing rules carry the reserve debit rule, the red-team checklist gains the breached-reserve probe (recompute the reserve, and treat a breach admitted only in prose as a Blocker), and `CONTEXT.md` gains **Reserve**.
- Executor vocabulary and platform-neutral wording. `armature-plan` §3 replaces its four-name `Executor` sentence with the table of everything the plugin ships — derive, cad, test, bringup, librarian, red-team, inventor, user — plus the combined form (`armature-bringup + user`) a bench leaf needs, the shape the demo had to hand-write as its own `CONTEXT.md` §4.5; this repo's **Executor** term names the same set and points at the table rather than restating it. The arm-and-drivetrain flavour comes out of three places a non-arm project had to translate by hand: the plan glossary's convention family now picks from the topology, offering a **floating base plus joints** (the body's pose in {W}, then each joint's axis and origin in its parent frame) as a convention in its own right, so a hopper states what it has instead of banning DH; the spec template's §6 gains a platform mapping — apex and ground range for reach, stride length and step height, turning radius and footprint, touchdown speed and landing attitude in place of a cycle time, an attitude envelope in place of a mount — and its topology table takes `F` for a free body; and `design-foundations.md` opens with how its wheeled-robot-with-an-arm examples read for mobile, legged, and aerial machines, down to mass climbing the trade-off matrix and the cheap failure moving to a stand or a tether. The spec interview's kinematic-sketch question points at the mapping.

- Derivation self-tests: **discovery by shape, not by name**. `run_all.py` collects every module in `analysis/model/` that defines `test_*` callables, ordered by the module-level `MILESTONE = (order, title)` each declares (a module without one runs last, titled by its file name — a forgotten constant costs a heading, never a check), and a new `test_derivation.py` imports that same discovery so `pytest` and `python run_all.py` cannot disagree about what the model's checks are. Each milestone module's `__main__` block runs its own discovered checks too, so no hardcoded list survives anywhere: a module added later — a `spring.py` for a plan task — and a test added to a module that already exists are both collected with no edit to either file. A guard test fails the run if discovery finds nothing, since an empty collection is a green run that checked nothing — which is how the demo's hand-written wrapper let Milestone 2's self-tests go unrun through two checkpoints. The derive checkpoint names both commands.
- Purchased custom parts: **sticker prices only**. A quotable specification, an RFQ cover note, and a quote register stay out of the plugin — a quote is a thing a vendor sends, not a thing a repository can produce — so cost comes from published prices instead. The datasheet index gains a **Price** cell (list price at its quantity break, dated by the row's `Retrieved`); a part whose vendor publishes none reads `quote only` and its cost stays a guess until a human asks; `init`'s standing rules make a cost estimate cite the row it read. `armature-librarian` gains the **stand-in** question — whether a catalogue part, or a combination of them, is close enough to bench-test a long-lead part's function with and never close enough to ship — answered in its survey ledger either way, `Nothing stock is close` included, so a negative answer is never a silence. The **corner sweep** becomes `armature-derive`'s (Milestone 3): the tolerances a design grants, exercised at the corners of their product, worst corner stated beside the nominal. `armature-cad`'s release transition sweeps before it dispatches the red team, so a margin that holds at nominal and fails at a corner is never the review's discovery. `CONTEXT.md` gains **Corner sweep** and **Stand-in**.
- Subagent dispatch: one rule, `references/subagent-dispatch.md` — send **two or three at a time** and let a wave land before the next goes out, because each subagent spends the dispatching session's context, tool calls, and share of the account session limit whether it succeeds or dies (the demo's five-librarian fan-out lost four to the 600 s stall watchdog and two re-dispatches to the session limit). Name the cost before a wave; size each run to one part or one slice of a field; prefer the agent that writes as it goes (the librarian's ledger survives a kill, an inventor's or red-team's single end-of-run write does not); read a leftover staging file before re-hunting. Every fan-out paragraph in `armature-spec` (Phases 2 and 4), `armature-derive`, `armature-plan`, `armature-cad`, and `armature-wayfind` points at it, and the `armature-librarian` and `armature-inventor` dispatch contracts carry the cap.
- Datasheet index: rows gain a **Clauses read** cell — the sections, tables, or pages actually verified — so a review probes what a row leaves open instead of re-asking what it already answers. The `File` cell now names the source kind: a cached PDF, a hand-written HTML snapshot, or an image plus the transcript beside it (many vendors publish no PDF); a source with nothing saveable points at the run's own record. `armature-librarian` opens one ledger per run under a single naming rule — a named-part run stages at `docs/datasheets/staging/<task>-<subject>.md` and is deleted at merge, a **survey** run writes `docs/datasheets/<task>-<subject>-<slice>.md`, which is permanent, so a survey that correctly confirms nothing and writes no index row still leaves its findings. A CANDIDATE row carries no decision until the user confirms it, in `init`'s standing rules, `armature-spec` Phase 4, and the red-team checklist — which, with the red-team's inputs, now reads the survey records too. `CONTEXT.md` gains **Survey file**.
- `armature-librarian`: gains Bash. Every run opens a staging file (`docs/datasheets/staging/<task>-<subject>.md`) before its first fetch and ledgers each row and cached file as found, so a stalled or rate-limited run leaves partial results; the file is the run's only report. A pre-confirmed P/N is cached in the run — the PDF fetched by `curl`, the index row shell-appended, never read-modify-written — while a candidate waits in staging for the user's confirmation and the agent's Merge step, which deletes the file once every row is merged. Dispatch paragraphs in spec, derive, and cad point at the contract. `CONTEXT.md` gains **Staging file**.
- `armature-plan`: the task unit is the session (roughly 100k tokens, one commit); parent tasks group lettered leaves; a review and its rework, a report, and a change of executor are cuts. Tasks are cut at every third-party wait so the agent-doable half has its own `Done when`. Estimates are sessions plus wall-clock, from an executor-aware starting table, with `Actual:` on closed leaves and a same-kind re-cut at each phase gate. `CONTEXT.md` gains **Session** and **Leaf**.

## 1.2.0 — 2026-08-30

Absorbs and adapts material from [Matt Pocock's skills](https://github.com/mattpocock/skills) (MIT, see `NOTICE.md`) and brings every agent-facing doc to one writing standard.

### New skills

- `armature-wayfind` — multi-session efforts charted as a map of decision tickets on the project's issue tracker (GitHub Issues or local markdown, auto-detected), resolved one ticket per session by the stage skills and agents.
- `armature-test` — test-driven development for robot software, default-on in Armature projects: red → green at unit and simulation level, bench seams handed to `docs/testing/bench-seams.md`.
- `armature-debug` — user-invoked bench debugging: a red-capable feedback loop before any hypothesis, then one variable at a time. Ships `scripts/human-loop.template.sh`, the shared step/confirm/capture primitive.
- `armature-bringup` — a plan's bring-up or verification test as an executable bash procedure, measurements recorded into its `docs/testing/` report.

### Renames

- `armature-concept` → `armature-pitch`, `armature-math` → `armature-derive`, `armature-teacher` → `armature-teach`. Every skill name now reads as a verb; agents keep their noun personas. Artifact paths (`docs/00-concept/`, `analysis/`) are unchanged.

### Changed

- Pitch, spec, and plan interviews run in frontier rounds via `AskUserQuestion` (recommended answer first), checkpoint each round, and send lookups to `armature-librarian` mid-interview.
- Project glossaries move from `docs/02-plan/` to the user project's `CONTEXT.md`; `init`'s `CLAUDE.md` template carries the inline-challenge rule and a three-gate ADR tier over `docs/decisions.md`.
- `armature-spec` and `armature-cad` draft questionnaires (`references/questionnaire.template.md`) for unknowns a third party holds.
- `armature-derive` gains `references/phase-boundaries.md`, the five-option context-boundary tree.
- Every `SKILL.md`, agent, and reference rewritten to the writing standard: duplicated rules single-sourced, one trigger per description branch, checkable done-conditions, hand-offs as Skill-tool calls. Agent descriptions carry their dispatch contracts.
- Repo-level `CLAUDE.md`, `docs/agents/issue-tracker.md`, and `docs/agents/domain.md` formalize the GitHub tracker and single-context domain docs.
- README gains a routing table and credits; `NOTICE.md` carries the MIT attribution.
